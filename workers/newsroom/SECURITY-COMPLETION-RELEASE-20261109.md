## Architecture and bindings (review only, not deployable configuration)

Exact entrypoints: `src/issuer-candidate.ts` → `dist/issuer-candidate.js`; `src/resource-s3-candidate.ts` → `dist/resource-s3-candidate.js`. **Do not** deploy `src/index.ts` provider/KV bundle or `src/resource-candidate.ts` with its native R2 option. New issuer and read-only resource each require a **fresh unique Worker name**, unique deploy target and own ingress namespace; no names are approved yet. Dedicated issuer SQLite Durable Objects: `ISSUER_GRANTS` (IssuerGrant), `ISSUER_GUARD` (IssuerGuard). Resource `ISSUER` is a Cloudflare service binding to the **new issuer only**, never a public proxy. Resource uses only bucket-scoped read-only R2 S3 credentials and **no** native R2 binding, original KEY_* secrets, OAUTH_KV or legacy endpoint.

Issuer bindings: `ISSUER_ORIGIN` (exact HTTPS origin), `ISSUER_CLIENT_ID` (registered ID), `ISSUER_CLIENT_SECRET_SHA256` (hash of private confidential-client secret), `ISSUER_RESOURCE_ID` (separate validator ID), `ISSUER_RESOURCE_SECRET_SHA256` (validator secret digest), `ISSUER_REDIRECT_URI` (exact client callback), `ISSUER_AUDIENCE` (resource HTTPS URL ending in /mcp), `ISSUER_EDITOR_ID` (allowlisted numeric GitHub ID), `ISSUER_GITHUB_CLIENT_ID`, `ISSUER_GITHUB_CLIENT_SECRET` (private secret), `ISSUER_GRANTS` and `ISSUER_GUARD` dedicated SQLite DO namespaces, `ISSUER_INGRESS_LIMIT` (dedicated Cloudflare ingress rate limit), `NEWSROOM_METRICS` (dedicated Analytics Engine dataset). **Every environment binding and deployment target is subject to reviewed approval and private provisioning**; do not include real secret values in a manifest.

Resource bindings: `RESOURCE_AUDIENCE` (equal to ISSUER_AUDIENCE), `RESOURCE_ISSUER` (equal to ISSUER_ORIGIN), `RESOURCE_CLIENT_ID` (equal to ISSUER_CLIENT_ID), `RESOURCE_VALIDATOR_ID` (equal to ISSUER_RESOURCE_ID), `RESOURCE_VALIDATOR_SECRET` (private secret whose SHA-256 equals issuer validator hash), `ISSUER` service binding, `RESOURCE_INGRESS_LIMIT` (independent per-location budget), `R2_READ_ENDPOINT` (account-specific HTTPS S3 API origin), `R2_READ_BUCKET` (exact approved bucket), `R2_READ_ACCESS_KEY_ID`, `R2_READ_SECRET_ACCESS_KEY` (distinct bucket-scoped Object Read only S3 credential), `NEWSROOM_METRICS` (separate Analytics Engine dataset). Storage adapter signs only GET and List; resource restricts MCP list/read, authenticates every request via issuer, and has no publication path.

**Monitor contract:** metrics writer `src/privacy-telemetry.ts` accepts only fixed category/surface plus count 1. No IP, token, token digest, URL, header, browser state, payload, personal identity or submission material is accepted. New emitter calls cover issuer denial, key rate-limit failures, refresh rejection, resource denial and service faults. It does **not** yet cover all required R2 error subclasses, emergency-epoch operator events or revocation failure as reliable distinct counters. **Absent sink silently omits counters**: release preflight MUST inspect binding presence and send/observe synthetic failure signals. Disable/query-redact invocation logs and ensure trace/log destinations cannot capture query strings, credentials, cookies, bodies, or exception messages. Do not enable broad request logging or store callback URLs. Add alerting and retention ownership before go-live.

**Rate limits:** issuer per-source `authorize`, `callback`, `consent`, `token` and `revoke` scopes are distinct. Failed confidential-client auth cannot spend authenticated token/revoke quota. A valid client credential is required before token/revoke admission. Internal `introspect` is deliberately **not** put into a public client-IP limiter, avoiding a shared service IP outage; its authenticating validator and active-token-only global budget remain. Resource MCP has its own budget. Binding missing/failed returns 503, exhaustion 429. Cloudflare rate limit is approximate/per location, so neither this nor the shared DO budget prevents a distributed many-IP attacker consuming the 60/min shared authorize quota. **F5 distributed login capacity remains NO-GO** until a tested compatible edge challenge/admission policy or another reviewed fair-capacity mechanism with multi-region proof exists. Do not just raise the shared quota; reserve independent revocation/Editor capacity, measure NAT/shared-egress behavior and GitHub/ChatGPT legitimate auth bursts.

## Evidence and independent security assessment

Reviewed: `issuer-candidate.ts`, `issuer-guard.ts`, `issuer-grant.ts`, `ingress-rate-limit.ts`, `issuer-github.ts`, `resource-candidate.ts`, `resource-s3-candidate.ts`, `readonly-s3-storage.ts`, and existing security regressions. Original grant model uses epoch-bound pending/code/access/refresh records, persistent atomic SQLite transitions, 300s upstream/code, 900s access, 28,800s refresh family, one-use replay records, and guarded internal CAS epoch invalidation. Callback uses one host-only secure 300s cookie; do not relax. No source path exposes internal invalidation to public callers. The source does not demonstrate remotely hosted real consent/revocation on the newest candidate; known prior browser attempt failed `invalid_browser_session`, root browser conditions unobserved.

Independent reviewer **not retained**; this is an implementer-led source review, not final independent sign-off. Review findings: (1) distributed public authorization/cost exhaustion still possible; (2) compromised bucket-wide read credential exposes unpublished submissions/editorial notes, though write paths are not exposed; (3) private issued secret rotation/epoch containment needs hosted rehearsal and identity proof; (4) Cloudflare analytics binding, alerts and audited logging settings not provisioned; (5) regional outage, disconnected issuance, callback and CI/deploy boundaries lack final hosted proof; (6) existing GitHub main protection/ruleset not enforced and archive automation pushes directly; (7) existing issuer service and working OAuth grants must remain unchanged. Strict account scope and S3-only read are good architecture boundaries but not production approval.

## Synthetic emergency recovery and failure scenarios

Existing predecessor tests prove local guard epoch compare-and-swap, persistence after cleanup/restart, expired/revoked grant denial and synthetic credential rotation/replay (review exact CI on PR #315). This branch adds public-ingress tests and telemetry invariants; it **does not** claim new hosted invalidateAll, secret rotation or multi-region tests. The disposable issuer previously deployed predates epoch implementation and cannot validate containment.

Hosted rehearsal on **new named disposable** issuer, fresh guard/grant namespaces and dummy S3 read bucket (not working Verification 04, S3 acceptance, or the legacy Worker):
1. Record source bundle hashes, new namespace and ingress inventory; verify that all name/route/service binding owners are distinct. Open only the disposable endpoints needed for the test.
2. Start synthetic grant and record only grant count/epoch/state category, never credentials. Test initial code exchange, two concurrent refresh requests, spent refresh replay, wrong audience/desk/read tool denials and timeout/restart with the actual service binding.
3. Disable **all** paths (workers.dev, preview/version, routes/custom domains, internal service callers); externally verify denial from distinct regions. Obtain operator-only `ISSUER_GUARD` binding; call `currentEpoch()`, then `invalidateAll(expectedEpoch)` once. A stale CAS retry must not invalidate fresh grants. Verify old access, refresh, pending and code all fail; a separately established fresh grant works, including after restart.
4. Prepare **disposable only** secret rotations in exact order: freeze ingress, rotate validator pair and confidential client private records in both peers, rotate dedicated GitHub App secret via its authorized operator, rotate bucket-scoped read S3 secret on matching resource, confirm old access fails only when epoch invalidated and old credentials no longer authenticate, check other test/production grant untouched. No production secrets/grants are used or copied.
5. Exercise failure injection: issuer unavailable, S3 403/429/5xx, storage timeout/redirect, region A/B clients, alarms and restart; record no-secret timestamps and resulting API code/metrics. Shut test endpoints, confirm settings and external denial, preserve immutable evidence but do not delete test resources until archive review.

**Stop conditions:** any cross-desk read, write route, log exposure, untracked ingress, old token acceptance after epoch invalidation, failure to reserve legitimate auth capacity, unbounded retry/cost, or absent alert owner means NO-GO. Never restore a pre-invalidation auth snapshot or downgrade to epoch-unaware code while ingress is open.

## Release sequence, rollback and GitHub governance

1. Freeze exact SHA, lockfile, built bundles and SHA-256 hashes; require supported Node CI tests/typecheck/five builds, publishing CI, static provenance, independent source review and *hosted* complete OAuth/GitHub + S3 synthetic acceptance.
2. Assign separate human security and operations reviewers. Document alert destination, on-call owner, threshold/budget and monitoring retention. Complete WAF/edge origin trust, cross-region availability and audit of all ingress paths; review actual ChatGPT flow before selecting limits.
3. GitHub administrator sets branch protection/ruleset for `main`: require pull request reviews, relevant passing `Newsroom readiness gate` and World publishing check, prohibit force pushes/deletion and administer bypass only through explicitly audited emergency policy. **Existing archive automation directly pushes to main**: inventory its current token/actions and choose a narrow archive-bot PR workflow or a narrowly scoped reviewed exception; do not blindly enable rules that break it or grant all Actions a bypass. Recheck compatibility with workflow path filters and unrelated PRs.
4. With separate explicit Presidential deployment authorization, provision *new* immutable issuer/resource names, new DOs and keys and new read-only bucket test scope. No test fixture may be deployed as production code. First deploy isolated no-live-bucket S3 resource; verify host lifecycle, full source hash, monitoring, boundaries and negative tools.
5. Independently approve attachment of production bucket-scoped **read-only** S3 credentials after disposable policy proves GET/List allowed, Put/Delete/other buckets denied. Never test writes against production. Confirm no new agent desk privileges: existing production Corindal/Korda/Varek/Federal bearer writer and Editor remain unchanged.
6. Connect the new dedicated Editor OAuth client and recheck every tool; watch health/error counts and cost; obtain Presidential approval separately for exact branch merge/production rollout. Monitor a controlled pilot. Site/World publication remains a different approval channel.

**Rollback:** freeze new onboarding, disable all new issuer/resource ingress and callers, validate complete shutdown. Retain original legacy Worker/grants and original R2 unchanged. Fail safe on issuer outage rather than cache authorizations; rotate only affected new credentials and invalidate corresponding epoch with reviewed internal operator control. Roll forward code after review, never restore expired/revoked SQLite state, never turn on old epoch-unaware code against newer live state. Region outage must be rehearsed with at least two independently located clients. Keep `main`, production, test and editorial queues isolated.
